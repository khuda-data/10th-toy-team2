WalkFit 데이터 전처리 과정에서 마주친 문제와 해결 방법을 시간순으로 기록합니다.
발표 자료는 이 문서의 "문제 → 해결 → 결과" 흐름을 그대로 스토리라인으로 쓰면 됩니다.
프로젝트가 진행될 때마다 이 문서에 새 절을 추가해서 계속 업데이트합니다.

## 1. 90m DEM의 한계와 5m DEM 자체 제작

**문제**: GPX의 `<ele>`(GPS 고도)는 노이즈가 심해서 못 쓰고, 대신 국토지리정보원 DEM으로 좌표별 고도를 매핑해서 경사도를 계산하는 방식을 쓰고 있었습니다. 그런데 처음 확보한 국토지리정보원 공개DEM은 **90m 해상도**였고, 우리가 쓰는 구간화 단위(30~50m)보다 격자가 더 커서 문제가 됐습니다.

**진단**: 홍민기\_평지\_6.gpx(평지 구간)와 홍민기\_가파른내리막길\_1.gpx를 30m 단위로 잘라 GPX ele / 90m DEM / 5m DEM 세 방식으로 경사도(%)를 비교했습니다.
- 90m DEM: 30m 구간이 90m 픽셀 하나 안에 통째로 들어가면 억지로 **0%**가 되고, 픽셀 경계를 넘으면 **-17%~+27%**까지 튀는 계단식 아티팩트 발생
- "평지"인데 -3.9%/-5.2%로 튀던 구간(9~10번)도 90m 방식에서 유래

**해결**: 국토정보플랫폼에서 받을 수 있는 **1:5,000 수치지형도 Ver2.0의 등고선 레이어(`N3L_F0010000.shp`, 필드 `등고수치`)**를 Delaunay TIN 기반 선형보간(`scipy.interpolate.LinearNDInterpolator`)으로 5m 격자화해서 직접 DEM을 만드는 방식으로 전환했습니다 (`src/dem_utils.py`, `python -m src.dem_utils` CLI로 누구나 자기 지역 것을 생성 가능).

**결과**: 같은 30m 구간 비교에서 분산이 94.55 → 16.21로 약 83% 감소, 문제였던 9~10번 구간 스파이크도 -3.9%/-5.2% → -1.8%/-3.0%로 완화. 팀 회의에서 이 방식을 표준으로 확정.

## 2. 팀원별 지역이 달라 DEM 커버리지가 부족했던 문제

**문제**: 5m DEM은 등고선을 받은 지역만 커버합니다. 6명(김재형·권동하·박준서·윤예진·최희수·홍민기)이 서로 다른 동네에서 측정했는데, 처음엔 홍민기(대전) 지역만 DEM이 있어서 나머지 5명 데이터는 고도 매핑이 안 됐습니다.

**해결 과정**:
1. 92개 GPX 파일의 좌표를 뽑아 사람별 bounding box 계산 → 역지오코딩(OpenStreetMap Nominatim)으로 행정구역 확인
   - 김재형: 용인시 기흥구 서천동, 권동하: 수원시 영통구 영통동, 박준서: 수원시 영통구 하갈동(행정동 "하동"), 윤예진: 화성시 동탄, 최희수: 과천시 원문동+별양동(두 동네에 걸침)
2. 국토정보플랫폼에서 지역별 등고선 SHP 다운로드 (총 9개 도엽: 대전067, 수원021/093/094, 용인003/004/015, 안양030/040)
3. 도엽별로 `dem_utils` CLI로 5m DEM 생성 → `data/raw/dem/`에 모아둠 → `build_dataset.py`가 여러 타일을 순서대로 시도해서 첫 유효값을 채우는 방식(`sample_dem_df`)으로 자동 매핑

**결과**: 16,221개 포인트 전부 DEM 고도 매핑 성공(NaN 0개), 635→623개 구간(이상치 필터링 후) 전원 데이터 확보.

**부수 발견**: 이 과정에서 `gpx_parser.py`의 파일명 정규식이 "N회차.gpx" 형식만 허용해서 홍민기 파일(`_1.gpx` 형식) 때문에 전체 파이프라인이 크래시하던 버그도 같이 발견해서 수정.

## 3. GPS 타임스탬프 불규칙으로 인한 속도 이상치

**문제**: `model_speed.py`의 k_slope 회귀(speed_ratio ~ slope_pct + slope_pct²) R²가 **0.0033**으로 사실상 무의미했습니다.

**진단**: `speed_mps` 최댓값이 **29.3 m/s(시속 105km, 도보로 불가능)** — 원인은 GPX 기록 간격이 불규칙해서(포인트 누락/몰림), 구간 경계로 뽑힌 두 포인트의 시간차(`dt_s`)가 실제와 안 맞는 경우가 있었기 때문입니다.
- 순간속도가 비정상적으로 큰 경우: `dt_s`가 1~4초로 찍혔는데 실제 이동거리는 30m대
- 반대로 속도가 비정상적으로 작은 경우: `dt_s`가 89초(중앙값 26초의 3배 이상)로 늘어져서 사람이 멈춰있던 시간이 이동시간에 섞임

**해결** (기준: 순간속도 15km/h 초과 / 연속 3초 이상 정지구간 제외):
- `remove_gps_jumps`: 원본 포인트 단계에서 point-to-point 순간속도가 15km/h를 넘는 포인트(GPS 튐)를 제거 후 재구간화. 구간 평균에서만 걸러내면 이미 오염된 누적거리(`cum_dist_m`)까지 같이 틀어져 있어 포인트 단계 정제가 필요했음.
- `moving_dt_s`: 정지 포인트를 지워도 남은 앞뒤 포인트의 실제 경과시간은 그대로라 `dt_s`만으론 해결이 안 돼서, 3초 이상 정지구간의 시간을 뺀 "이동시간"을 따로 합산해 `speed_mps = dist_m / moving_dt_s`로 계산.

**결과**: `speed_mps` 최댓값 29.3 → 2.64 m/s(시속 9.5km, 정상 범위), `slope_pct`-`speed_mps` 상관계수 -0.058 → -0.265(경사가 클수록 느려지는 물리적으로 맞는 방향), k_slope 회귀 **R² 0.0033 → 0.0831 (약 25배 개선)**.

## 4. 데이터 2차 수집 반영 — 표본 불균형이 R²에 미치는 영향

**배경**: 홍민기가 GPX를 29건 추가 수집(총 92→130개 파일)하면서 재전처리를 돌렸습니다.

**결과**: 구간 수는 623 → **969개**로 늘었는데, k_slope 회귀 R²는 오히려 **0.083 → 0.038**로 낮아졌습니다.

**원인**: 늘어난 데이터가 거의 다 홍민기 것이라, 전체 969개 구간 중 홍민기 비중이 **47%(454개)**까지 커졌습니다. `k_slope` 회귀는 전원 데이터를 합친(pooled) 하나의 모델이라, 특정 한 사람의 비중이 지나치게 크면 그 사람의 개인적인 노이즈/패턴이 "공통 경향"인 것처럼 회귀에 과대 반영되면서 전체 적합도가 오히려 흔들릴 수 있습니다. 즉 **표본 수가 늘어난다고 항상 R²가 좋아지는 건 아니고, 사람별 표본이 고르게 늘어야 의미가 있다**는 걸 보여주는 사례입니다.

**시사점**: 발표에서 "데이터 총량"보다 "사람별 균형"이 왜 중요한지 보여주는 근거로 쓸 수 있습니다. 다음 데이터 수집 때는 특정 인원에 몰리지 않게 독려하는 게 좋아 보입니다.

## 다음 단계 / 열린 이슈

- **R²가 여전히 낮고, 표본이 늘어도 자동으로 좋아지지 않음**을 확인함(위 4번 참고). 사람별 개별 회귀, 또는 사람 수를 가중치로 보정한 회귀(예: 사람별 균등 가중) 등을 다음에 시도해볼 만함.
- 세그먼트 목표 길이(현재 40m) 조정은 아직 시도 안 함.
